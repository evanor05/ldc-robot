# 每轮 Nav2 速度通道隔离（2026-11-17）

## 本批行为

Bridge 不再订阅共享 `/cmd_vel_auto`。每次 `begin` 创建新的速度输入：

```text
/ldc/velocity/b<Bridge启动UUID>/r<本轮UUID>
```

`b`/`r` 前缀保证ROS话题的名称段不以数字开头。UUID是运行标识，不是秘密或加密认证。

新增 `scripts/velocity_channel.py`：可靠、volatile、depth=1；轮换前先撤销旧回调代次，再销毁旧DDS reader。即使旧生产者继续发送，或者旧回调已排队，不能进入新一轮。停止、退出或销毁Bridge会关闭通道；订阅创建异常保持关闭，不回落共享输入。

后端等待Bridge返回 `velocityTopic`，校验后作为 Nav2 的 `cmd_vel_output`。未返回或返回旧共享话题时，撤销准备状态并拒绝启动；不会静默使用旧通道。运行配置记录实际话题，状态新增 `velocityChannel={bootId,epoch,topic}`，旧字段保留。

这是**每轮begin的运行隔离**。同一轮内的cancel/暂停和再次启用不是新的run epoch；本批没有宣称普通Twist携带了授权token，也没有完成“每次授权都有新速度来源”的协议。该边界待指定模型进一步裁定，自动探索入口仍保持隔离。

未修改实车动力、导航参数、MCU固件、地图或摄像头；不需要刷写或安装系统依赖。重启控制台后端才会替换已运行的旧Bridge；本批没有中断用户正常服务。独立legacy Nav2 launch仍输出中间话题，不能直接向新的Bridge运行注入速度。

## 新发现：取消空列表不代表没有未终止目标

本批在独立Domain198的 `/ldc_probe/navigate_to_pose` 上使用真实ROS ActionServer、CancelGoal和GetResult验证：

1. 执行中的目标收到CancelAll后返回code=0和该目标UUID。
2. 目标仍在取消中、GetResult尚未完成时，第二次CancelAll返回code=0但列表为空。
3. 只有执行器明确结束后，GetResult才返回CANCELED。

因此重启清理必须合并保留已观察到和已发请求的UUID，逐个确认终态。不能用第二次空列表清除未确认屏障。证据在 `cancel-contract.json`、`cancel-contract.log`、`probe_cancel_contract.py`；没有任何速度发布。

本地 `action_msgs/srv/CancelGoal.srv` 和生成的 `NavigateToPose.Impl.GetResultService` 已核对。官方 [ROS 2 Action 设计](https://design.ros2.org/articles/actions.html#cancel-goal-service)也区分取消响应与最终结果。当前实现仍未包含完整重启对账，本探针只是语义证据。
